# Shopper Assist

Turn a messy shopping list — typed or photographed — into the shortest walking
route through a store.

You type something like `2 bananas, a dozen eggs, cocacola, band aids` or
snap a photo of a handwritten list. Shopper Assist extracts the individual
items, matches each one against a product catalog even if the wording is
off (typos, abbreviations, brand vs. generic), checks what's actually in
stock, and returns a turn-by-turn walking route — entrance to every shelf
you need to checkout — over a demo grid store, plus an SVG map of the path.

## How it works

1. **Extract** — Gemini (`gemini-3.6-flash`) turns free text or a list photo
   into structured `{name, qty, unit}` items (`backend/src/services/extraction.js`).
2. **Match** — each item name is matched against the `products` catalog using
   a hybrid of lexical trigram similarity (Postgres `pg_trgm`) and semantic
   similarity (Gemini embeddings + pgvector cosine search over an HNSW
   index). Candidates from both are merged and scored; a match only counts
   above a confidence threshold (`backend/src/services/matching.js`).
3. **Check stock** — matched SKUs are checked against `inventory`; anything
   out of stock or unmatched is set aside and reported instead of silently
   dropped (`backend/src/services/inventory.js`).
4. **Route** — the shelf locations of everything left feed a route
   optimizer: Dijkstra for shortest paths between stops, then an
   open-path TSP solve (brute-force for ≤9 stops, nearest-neighbor + 2-opt
   otherwise) from entrance → all needed shelves → checkout
   (`backend/src/services/routing.js`).
5. **Show it** — the frontend renders the extracted list, anything
   unmatched or out of stock, step-by-step walking directions, and an SVG
   map of the store with the route drawn on it. A separate aisle-by-aisle
   product directory lets you browse the catalog on its own.

The store itself is synthetic: 8 aisles (Produce, Dairy & Eggs, Bakery,
Meat & Seafood, Frozen, Pantry & Dry Goods, Beverages, Household &
Personal Care), ~200 products, generated by `data/generate_store_data.py`
as a reproducible graph of aisle junctions and shelf nodes.

## API

| Method | Path       | Purpose                                                         |
|--------|------------|------------------------------------------------------------------|
| GET    | `/health`  | Liveness check                                                   |
| GET    | `/aisles`  | Aisle directory (category → product names)                       |
| POST   | `/extract` | Text or photo → structured `{name, qty, unit}` items             |
| POST   | `/match`   | Item names → matched SKUs with confidence + alternates           |
| POST   | `/route`   | SKUs → optimal walking route                                     |
| POST   | `/plan`    | Full pipeline: extract → match → filter stock → route (what the frontend calls) |

All errors return `{detail: "..."}` (503 if Gemini isn't configured, 400
for missing input, 500 otherwise).

Stack: Node.js/Express backend, React (Vite) frontend, Postgres (Supabase,
with `pg_trgm` + `pgvector`), Google Gemini for extraction and embeddings.

## Run locally

Prereqs: Node.js 24 LTS, a Supabase project (Postgres + pgvector, hosted), a Gemini API key
for list extraction/semantic matching.

```
# 1. Backend deps
cd backend && npm install

# 2. DB (one-time): set DATABASE_URL in .env to your Supabase connection string
#    (Project Settings -> Database -> Connection string -> URI), then:
cd backend && npm run db:schema && cd ..
pip install -r data/requirements.txt
python data/seed.py                # requires Python only for the one-off seed script
python data/embed_catalog.py       # backfills semantic embeddings, needs GEMINI_API_KEY

# 3. Backend
cd backend && node src/server.js

# 4. Frontend (separate terminal)
cd frontend && npm install && npm run dev
```

Open http://localhost:5500. Set your Gemini key in `.env` (`GEMINI_API_KEY=`) to enable
`/extract` and `/plan` (list photo/text parsing) and semantic `/match`. `/match` and `/route`
work without a key via `pg_trgm` lexical matching alone.

## Notes

- Postgres is **Supabase**, both locally and in production — one hosted database, no local
  Postgres/Docker setup needed. Semantic matching uses **pgvector** (HNSW index, cosine
  distance via the `<=>` operator), which Supabase provides natively. Embeddings are
  truncated to 768 dims (from the model's native 3072) to stay under pgvector's HNSW index
  dimension ceiling and keep the index small.
- `db.js` sets `ssl: { rejectUnauthorized: false }` on the `pg` Pool — Supabase's cert chain
  isn't fully verified under the newer strict `pg`/`pg-connection-string` default for
  `sslmode=require`, so SSL is configured explicitly rather than via a `?sslmode=` query param.
  The connection is still encrypted; this only skips full chain verification (the standard
  way node-postgres connects to Supabase).
- `DATABASE_URL` passwords need URL-encoding for special characters — `@` becomes `%40`, etc. —
  since the password sits in the URL's userinfo segment before the host.
- `data/generate_store_data.py`, `data/seed.py`, and `data/embed_catalog.py` remain Python —
  they're one-off data-prep scripts, not part of the running service.
- Gemini model names drift — this repo currently targets `gemini-3.6-flash` (extraction) and
  `gemini-embedding-001` (embeddings); check `GET /v1beta/models` on your key if calls 404.
